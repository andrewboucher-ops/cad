The GuardM8 ↔ CCCS bridge

Two data paths between GuardM8/AURA and Echelon's dispatch console: GuardM8 pushing jobs into CCCS, and CCCS pushing emergency-button alerts out to AURA. Written for whoever's wiring up GuardM8's side of both.

Direction 1 — inbound

Dispatching a job into CCCS

GuardM8 raises an alarm and wants a unit dispatched. One POST creates a real, dispatchable job in CCCS's queue — same shape a call-taker creates by hand, visible on the control room board immediately.

Endpoint

POST https://comms.echeloncic.com/api/integrations/guardm8/jobs

Headers

HeaderValue
x-guardm8-secret1c4b8409ce1b604a46d0d5889f1fdf9c3fbb792b580184c5
content-typeapplication/json

Body

FieldNotes
locationrequired* — free-text address. *or site, if the premises is a known CCCS site.
priorityoptional — RED/AMBER/GREEN/ROUTINE or plain words (critical, high…) / P-codes. Defaults to GREEN.
incident_typeoptional — e.g. "PANIC ALARM". Defaults to ALARM.
descriptionoptional
calleroptional — defaults to GuardM8.
external_refrecommended — your alarm ID. Resending the same value returns the existing job instead of duplicating it.
lat / lonoptional
required_resourcesoptional — defaults to 1.
what3words, notes, keyholderoptional

Example

curl -X POST https://comms.echeloncic.com/api/integrations/guardm8/jobs \
  -H "x-guardm8-secret: 1c4b8409ce1b604a46d0d5889f1fdf9c3fbb792b580184c5" \
  -H "content-type: application/json" \
  -d '{
    "external_ref": "GM8-ALM-9001",
    "priority": "critical",
    "incident_type": "PANIC ALARM",
    "location": "Oakwood DVR 2, Tadcaster",
    "description": "Panic button activated, zone 3",
    "caller": "GuardM8 Controller"
  }'

Response — 201 on create, 200 when external_ref replays an existing job:

{
  "id": 11,
  "reference": "INC-2026-00135",
  "incident_type": "PANIC ALARM",
  "priority": "RED",
  "location": "Oakwood DVR 2, Tadcaster",
  "status": "CREATED",
  "external_source": "guardm8",
  "external_ref": "GM8-ALM-9001",
  "resources": []
  // …plus created_at, caller, description, notes, etc.
}

Errors

401missing or wrong x-guardm8-secret
400neither location nor site given
Direction 2 — outbound

Receiving emergency alerts in AURA

When an officer's or MDT's emergency button is pressed, CCCS publishes an alert over MQTT to AURA. The transport is wired and verified reachable — the message shape AURA's parser wants is still being confirmed, so publishing is currently switched off.

Transport

FieldValue
Broker192.168.7.31:1883 · plain TCP, username + password
Publish topicarc/rx/cccs — the "CCCS" provider registered in AURA
Connectionpersistent, one client for the process lifetime, reconnects on drop
Triggerany officer/MDT emergency-button press (physical or on-screen)
Feed timeoutAURA's provider config raises an alarm if this topic is silent for 300s

Current payload attempt (unconfirmed)

{
  "acct": "8581",          // Echelon Control Centre
  "zone": "0",
  "event": "PA",             // SIA: panic alarm
  "description": "Emergency button activated",
  "callsign": "P101",
  "lat": 53.601, "lon": -0.203,
  "timestamp": "2026-09-14T13:45:04.003Z"
}
What AURA's side needs to confirm
  • Exact field names the arc/rx/cccs provider's parser expects — a first attempt with acct/zone/event/description still returned an "Unparsed signal".
  • Whether event should be a SIA code (PA) or something else in CCCS's own vocabulary.
  • Whether a heartbeat is required to hold the feed-timeout watchdog open between real alerts, and on what cadence.

Two test messages from earlier probing are still sitting un-acknowledged in the AURA queue as "Unparsed signal via cccs" — safe to Ack and clear.
